# ONL.IS — инструкции к проекту

Система управления кофейней / общепитом / ритейлом. PHP 7.4, MySQL (InnoDB), jQuery + Bootstrap, без фреймворка. Мультитенантность: у каждого клиента свой поддомен и своя БД.

Подробные стандарты интерфейса, форм, JS, RBAC и API модулей лежат в [_instructions.txt](_instructions.txt). Перед любой работой с интерфейсом или новым модулем читай нужный раздел оттуда. Этот файл — краткая выжимка и принципы, которых в `_instructions.txt` ещё нет (товароучёт).

## Как работать

- Правь только нужный фрагмент, не переписывай файл целиком, если об этом не просили.
- Не расширяй задачу сам. Всё, что видишь по пути, но что вне запроса, называй отдельным списком, не чини молча.
- Не делай `git commit` и `git push`, пока пользователь явно не попросил.
- PHP, MySQL и Node в среде Claude Code недоступны: код нельзя запустить. Проверка идёт ручной трассировкой и дампами БД (Adminer), которые присылает пользователь. Не пиши «проверено», если код не выполнялся. Говори, что именно проверено и как.
- Перед вёрсткой делай анализ UI/UX: группировка полей, отступы (`mb-3`), понятные подписи.
- Не выдумывай функции. Реальный список функций `fncs.php` — в `_instructions.txt` (раздел «Реальные функции fncs.php»). `fncLastId()` не существует: используй `$pdo->lastInsertId()`.
- Язык общения, комментариев и сообщений пользователю — русский.

## Архитектура

- Вход: `index.php` → SPA-каркас `_main.php`. Меню строится из `menu_map.php`, разделы модулей — из `modules_map.php`.
- Фронтовые фрагменты: `_books_X/*.php`, `_docs/*.php`, `_payments/*.php`. Логика раздела — в `<папка>/js/*.js`.
- API модулей: `app/app_X.php`, один `switch ($action)`, ответ всегда HTTP 200 и JSON. Ключи маршрутов в `app/includes/paths.php` намеренно не совпадают с ключами `modules_map.php`.
- Фронт ходит в API через `send_request($data, 'модуль')` (PHP) или `fncMyAjax` (JS). Внутри `app_X.php` не вызывай другие `app_Y.php`, только прямой SQL.
- Авторизация в `app_X.php`: `fncApiAuth`, потом `fncCan($perms, 'slug')` в каждом `case`. Во фронтовых фрагментах права берутся из `fncRequireSession()['rules']`.
- Запросы к БД только через `fncQuery()` (PDO prepared). Он не бросает исключения, при ошибке пишет в лог и возвращает `false`. Всегда проверяй результат.
- Стиль SQL: без обратных кавычек, короткие алиасы таблиц.
- `case` в `switch` должны быть уникальны: дубль PHP не замечает, второй блок становится мёртвым кодом.

## База данных

- utf8mb4. Флаги — `TINYINT(1) NOT NULL DEFAULT 0/1`. Деньги — `DECIMAL(10,2)`. Типы FK обязаны совпадать с типом `id` (`INT(10) UNSIGNED`), иначе ошибка 1215.
- `created_at/created_by/updated_at/updated_by` там, где нужно по логике. `updated_*` — `NULL`, пока запись не редактировали.
- Состояние, которое выводится из наличия связанных данных, отдельным флагом не заводится.
- Мягкое удаление — `actual` (NULL = архив), доступ — `is_active`. Не смешивать.
- Схема меняется только миграциями (SQL-файл или ALTER, который пользователь выполняет сам). Показывай SQL пользователю, сам в БД ничего не пиши.
- Именованные плейсхолдеры в PDO: при `ATTR_EMULATE_PREPARES => false` одно и то же имя нельзя использовать дважды в одном запросе. Давай разные имена (`:whout`, `:whin`).

## Права доступа (RBAC)

- Слаги образуют линейную цепочку: `inventory` → `inventory.documents` → `inventory.documents.<code>` → `...<code>.view`.
- `fncCan` смотрит только вверх: родительский слаг покрывает потомков, наоборот не работает.
- Новый модуль: `INSERT` в `permissions`, `INSERT` в `roles_permissions`, строка в `menu_map.php`, проверка `fncCan` в каждом `case`, `canDo` в JS.
- Товароучёт дополнительно ограничивается организациями: `fncOrgScope()` (полный `inventory` обходит ограничение, иначе организации из `organization_staff` с `date_end IS NULL`) и `fncDocAccess($row, $edit)`. Просмотр требует слаг `.view`, изменение — слаг редактирования. Проверка закрыта по умолчанию: нет `organization_id` — нет доступа.

## Товароучёт (`app/app_docs.php`, `_docs/`)

- Жизненный цикл документа: `draft → posting → posted`. Переход в `posting` атомарный, до транзакции. Любая ошибка (`catch (Throwable)`) возвращает документ в `draft`. Зависшее проведение (≥ 10 минут) пользователь возвращает в черновик кнопкой.
- На складе одновременно может быть только один документ в статусе `draft`/`posting`. Это сознательное правило, обеспечивается блокировкой строки в `objects`. Гонки между документами одного склада багом не считаются.
- Складской учёт: FIFO-партии. Регистры `stock_ledger` (бегущие `total_quantity/total_sum`, `is_last`, `quantity_remaining` у приходных строк), `stock_ledger_consumption` (списание по партиям), `settlements_ledger` (минус = мы должны).
- Резервы партий при ручном распределении (`document_item_batches`, `document_item_ingredient_batches`) виртуальные. Физически остаток списывается только при проведении.
- Количества: `decimal(12,3)`, допуск `QTY_EPS = 0.0005`, округление `fncRoundQuantity()`, ввод не более трёх знаков. Цены `decimal(10,4)`, деньги в сумме — 2 знака. Средняя цена строки считается точно, как Σ(кол-во × цена партии) / кол-во. Сумма строки — сумма округлённых сумм по партиям.
- Вывод: количества — `fncFormatQuantity` (PHP и JS), деньги — `fncFormatNumber`.
- Отмена проведения (`unpost_document`) возможна, только если:
  1. все пары (номенклатура + склад) документа в `stock_ledger` имеют его `is_last`;
  2. строка взаиморасчётов с контрагентом последняя;
  3. на складах документа нет документов в `draft`/`posting`.
  Строки откатываются в порядке убывания `id`. `price/sum` строк обнуляются только для `writeoff` и `sf_production`. Кнопка в интерфейсе показывается, лишь когда отмена реально возможна (`can_unpost` считает сервер).
- Любое проведение и отмена идут в одной транзакции с блокирующими чтениями (`FOR UPDATE`). Помни про REPEATABLE READ: обычный `SELECT` видит снимок транзакции, блокирующий — свежие данные.
- Тексты ошибок с пользовательскими данными экранируй (`htmlspecialchars`): `fncShowFormError` вставляет сообщение через `.html()`.
- В JS пользовательский текст вставляй через `.text()`, не `.html()`.
- После правки JS поднимай версию в `<script src="...?NNN">` соответствующего PHP-файла, иначе браузер возьмёт кэш.

## Проверка изменений

- Нет PHP/Node, поэтому для базовой проверки баланса скобок используй скрипт-счётчик (PowerShell), а не `php -l`.
- Для учёта сверяй дампы вручную: остатки партий, `is_last`, итоги `total_quantity/total_sum`, расшифровку по `stock_ledger_consumption`, баланс `settlements_ledger`. Сверяй до и после проведения, после отмены и после повторного проведения.
- Прямо говори, что осталось непроверенным (права и организации под вторым пользователем, экранные подсказки и т. п.).
